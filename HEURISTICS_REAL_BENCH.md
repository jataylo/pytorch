# Heuristics Real Benchmarking Feature

## Overview

This feature enables comprehensive validation of pointwise heuristics by benchmarking **ALL** valid configurations and comparing predicted scores against actual performance.

## New Configuration Option

### `TORCHINDUCTOR_HEURISTICS_REAL_BENCH`

**Default**: `1` (enabled)

Controls whether the heuristics system benchmarks all configs or just the top-N:

- **When `1` (enabled)**:
  - Benchmarks ALL valid configurations generated by heuristics
  - Stores predicted scores for each config
  - Captures actual timing during autotuning
  - Prints validation summary showing:
    - Which config heuristics predicted would be best
    - Which config was actually fastest
    - Performance gap between prediction and reality
    - Accuracy rating (Excellent <5%, Good <15%, Acceptable <30%, Poor >30%)

- **When `0` (disabled)**:
  - Only benchmarks top 5 configs (faster tuning)
  - No validation summary
  - Optimized for production use

## Usage

### Enable Full Benchmarking (Default)

```bash
# Explicitly enable (default behavior)
export TORCHINDUCTOR_HEURISTICS_REAL_BENCH=1
python my_model.py
```

### Fast Mode (Top-5 Only)

```bash
# Disable for faster tuning
export TORCHINDUCTOR_HEURISTICS_REAL_BENCH=0
python my_model.py
```

## New API Functions

### 1. `PointwiseHeuristics.score_specific_config(config, problem_metadata)`

Score any specific configuration for a given problem.

```python
from torch._inductor.codegen.triton_heuristics_pointwise import PointwiseHeuristics

config = {'XBLOCK': 256, 'num_warps': 4}
problem_metadata = {
    'dimensions': (8192,),
    'total_elements': 8192,
    # ... other metadata
}

result = PointwiseHeuristics.score_specific_config(config, problem_metadata)
print(f"Score: {result['score']:.4f}")
print(f"Valid: {result['valid']}")
print(f"Details: {result['details']}")
```

**Returns**:
```python
{
    'score': 0.8234,  # Overall predicted performance (0-1)
    'valid': True,    # Whether config is valid
    'details': {      # Factor breakdown
        'load_balance': 0.985,
        'launch_overhead': 0.920,
        'occupancy': 0.950,
        'grid_granularity': 0.875,
        'composite': 0.8234,
        'num_blocks': 32,
        'threads_per_block': 256
    },
    'config': {'XBLOCK': 256, 'num_warps': 4}
}
```

## Implementation Details

### Dimension Validation Relaxation

The validation logic now allows smaller block sizes when the overall grid is reasonable:

**Before**: Enforced `min_block=16` for any dimension > 32

**Now**: Allows `min_block=4` if:
- Dimension ≤ 32, OR
- Problem is 3D, OR
- **Total grid blocks ≤ 1024** (NEW!)

This prevents filtering configs like `XBLOCK=8, YBLOCK=8` for problem `(32, 1024)` when they produce the same grid as larger block configs.

### Data Flow

1. **Prediction Phase** (`_apply_pointwise_heuristics`):
   - Generates all candidate configs
   - Scores each config
   - Stores predictions in `_HEURISTICS_VALIDATION_DATA`
   - Returns ALL valid configs (if REAL_BENCH=1) or top-5 (if REAL_BENCH=0)

2. **Benchmarking Phase** (`bench` method):
   - For each config, measures actual timing
   - Stores timing in `_HEURISTICS_VALIDATION_DATA`

3. **Summary Phase** (`autotune_to_one_config`):
   - After best config selected
   - Calls `_print_heuristics_validation_summary`
   - Compares predictions vs reality

### Storage Structure

```python
_HEURISTICS_VALIDATION_DATA = {
    "(32, 1024)": {  # problem_key
        'problem_metadata': {...},
        'predicted_scores': [
            (0.8378, {'XBLOCK': 4, 'YBLOCK': 16, 'num_warps': 1}),
            (0.8334, {'XBLOCK': 4, 'YBLOCK': 32, 'num_warps': 1}),
            ...
        ],
        'actual_timings': [
            (0.000142, {'XBLOCK': 8, 'YBLOCK': 16, 'num_warps': 2}),
            (0.000156, {'XBLOCK': 4, 'YBLOCK': 16, 'num_warps': 1}),
            ...
        ]
    }
}
```

## Performance Impact

### REAL_BENCH=1 (Default)

- **Pros**:
  - Complete validation of heuristics
  - Identifies when predictions are suboptimal
  - Helps tune heuristic weights/factors
  - No performance loss in inference (only affects first compilation)

- **Cons**:
  - Longer first-time compilation
  - More benchmark iterations
  - For 45 configs: ~45x more benchmarking vs top-5 only

### REAL_BENCH=0 (Fast Mode)

- **Pros**:
  - 9x faster autotuning (5 configs vs 45)
  - Minimal compilation overhead
  - Production-ready

- **Cons**:
  - No validation data
  - May miss better configs if heuristics are inaccurate

## Use Cases

### Development & Tuning

Use `REAL_BENCH=1` when:
- Developing or refining heuristics
- Analyzing heuristic accuracy
- Debugging config selection
- Collecting data to improve scoring factors

### Production

Use `REAL_BENCH=0` when:
- Deploying models to production
- Fast compilation is critical
- Heuristics have been validated
- Minimal overhead is desired
