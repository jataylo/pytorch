# FlyDSL SIMD backend: pointwise, reduction, scan and foreach kernels

The FlexAttention path lowers a few FX subgraphs into a hand-written kernel. This backend
goes the other way: it replaces Triton as the code generator for Inductor's ordinary
fused kernels -- pointwise, reduction, scan, transposing and combo (foreach) kernels --
and emits a FlyDSL module per kernel instead of a Triton one. It is **ROCm only,
experimental and off by default**.

```bash
TORCHINDUCTOR_FLYDSL_SIMD=1 python train.py          # FlyDSL where it can, Triton elsewhere
TORCHINDUCTOR_FLYDSL_SIMD_STRICT=1 ...               # raise instead of falling back
TORCHINDUCTOR_FLYDSL_SIMD_STAGES=norm,combo ...      # FlyDSL for these kernel classes only
```

or `torch._inductor.config.flydsl.simd = True` / `flydsl.simd_strict = True`.

Every kernel it refuses goes to Triton unchanged, with the reason counted in
`counters["flydsl_simd"]` (`flydsl_simd_counters()` returns them). On the ten models of
the [model suite](#whole-models) nothing falls back: every pointwise, reduction and
foreach kernel Inductor builds for them is generated by FlyDSL.

## How a kernel is generated

The scheduler hands `FlyDSLSIMDScheduling.codegen_node_schedule` a fused node schedule.
It picks a tiling -- `{x}` for pointwise, `{x, r0_}` for a reduction or scan, `{y, x}`
when Inductor's tiling analysis finds a transpose -- and drives the normal `SIMDKernel`
codegen with `FlyDSLKernel`, whose ops overrides print every op as a call into `fdp`
(`fdp.add(tmp0, tmp1)`, `fdp.vload(...)`). Any `FlyDSLUnsupported` raised on the way rolls
the attempt back and the schedule is handed to Triton. A combo kernel is split into
groups of at most `combo_kernel_max_num_args` buffers, each generated as one FlyDSL
kernel whose blocks dispatch on the sub-kernel. Inductor's mix-order reductions (a row
and a column reduction of one input fused, as in a norm's backward) and nested
reductions have only Triton kernels, so with FlyDSL the scheduler does not form them
and FlyDSL generates their reductions apart: BERT training 29.83 -> 29.47 ms a step,
all 130 of its kernels on FlyDSL.

The emitted module holds the kernel and launcher as plain functions, decorated with
`@flyc.kernel` / `@flyc.jit` only when something compiles them, plus `_precompile` and
`_main`. In the compile worker `_precompile` compiles the kernel and writes its code
object (`<module>.<kernel>.hsaco`) beside the module; `_main` launches that through
`torch._C._StaticCudaLauncher`, so the main process never traces, JITs a host stub or
even decorates the kernel, and falls back to `flyc.compile` only when the file is missing
(for example when Inductor compiles in-process). FlyDSL traces the kernel in Python, so
the generated code is
ordinary Python that runs once at compile time: `range_constexpr` loops are unrolled
during tracing, and `fdp` keeps trace-time dictionaries (vector-load, vector-store and
persistent-row caches) that turn Inductor's per-element ops into vector instructions.

### Kernel classes

`FlyDSLKernel.stage` names the class a kernel falls in; `TORCHINDUCTOR_FLYDSL_SIMD_STAGES`
takes a comma-separated list of them and sends the rest to Triton, which is how the
[ablation](#which-stages-to-upstream-first) below was measured.

| stage | kernels | layout |
| --- | --- | --- |
| `pointwise` | elementwise, broadcasts, gathers/scatters, RNG, atomics | a thread owns `unroll` runs of `ept` contiguous elements, interleaved so each wave instruction covers one span |
| `tile` | transposes, NCHW <-> NHWC, head permutes | 32x32 LDS tile (pitch 33), 128-thread blocks, read and written with two thread mappings |
| `row` | pure reductions along a contiguous row (sum, amax, argmax, ...) | `tpr` lanes a row, `xunroll` rows a group, combined by DPP/butterfly shuffles, through LDS past a wave |
| `norm` | reductions whose result is used in the same kernel: softmax, layernorm, rmsnorm, cross-entropy and their backward | as `row`, with the row held in registers between passes when it fits |
| `column` | reductions along a strided dimension, split reductions (weight gradients, BatchNorm statistics) | 64 lanes along x, the waves of a block split r and combine through LDS |
| `scan` | `cumsum`/`cumprod`/associative scans along a row | a row's lanes scan their runs, then a cross-lane scan and a carry from the runs before |
| `combo` | foreach kernels (optimizer steps) | one block range per sub-kernel |

Rows of at most 16 vector runs a thread are *persistent*: unrolled entirely, held in
registers, and re-read from the trace-time cache by later passes (a layernorm's normalize
pass does not reload, and a row stored then re-read later in the kernel is forwarded
from the registers of the store). Longer rows run an `scf.for`.

**Chunked combines.** Inductor asks for one combine per element. Since a thread holds a
whole chunk at trace time, `fdp` combines it at once: sums as a balanced tree, online
softmax with one rescale per chunk, and -- for persistent rows -- softmax and variance in
two passes over registers (max then exp-sum; sum then squared deviations), as Triton does.

**Launch parameters** are written into the kernel as a comment, e.g.
`# row reduction xnumel=4096 rnumel=768 ept=4 unroll=1 tpr=64 stride=1 xunroll=1 persistent=True`,
and `TORCHINDUCTOR_FLYDSL_SIMD_TUNE="key=value,..."` overrides any of them for
experiments:

| key | applies to | meaning |
| --- | --- | --- |
| `ept`, `unroll` | pointwise | elements a run, runs a thread |
| `row_tpr`, `row_unroll`, `xunroll` | row, norm, scan | lanes a row, runs a lane, rows a lane group |
| `col_stride`, `col_unroll` | column | lanes along x, r steps a thread |
| `col_pair` | column | `0` keeps one column a lane in bf16/f16 column reductions |
| `threads` | all | block size |
| `slp` | all | LLVM's SLP vectorizer on (`1`) or off (`0`); default on for pointwise and tile kernels, off for reductions, where it costs 5-15% |
| `merge_rows` | row | `0` stores short rows' results one row at a time from lane 0 |
| `force_flat` | tile | `1` runs a transpose with the flat layout |
| `autotune` | pointwise, tile, short rows | `0` keeps the heuristic's launch parameters instead of timing candidates on the first call |
| `wload` | pointwise | `0` turns off the wave-uniform scalar load of per-channel operands |
| `atomic_pair` | pointwise | `0` issues 16-bit atomic adds one element at a time |

The largest wins are normalizations, where Triton's default (non-autotuned) reduction
configs leave bandwidth on the table: chunked online softmax, two-pass variance and wide
vector loads reach 1.6-3 TB/s against Triton's 0.4-0.85. RNG wins by drawing four
Philox outputs per call for four consecutive offsets. Five cases lose:
`nchw_to_nhwc_f32` and `transpose_f32` (2-6%), whose 4-byte tile rows cannot be written
with stores as wide as Triton's; `softmax_bwd_512` (8%), whose autotune pick is bimodal

where every block shape tried is at or behind Triton; and `add_layernorm_768` (3%).
`cast_bf16_24M`, which lost by 4%, now wins by 7%: a pointwise kernel whose stores are
all narrower than its widest load (a narrowing cast) gives each thread twice the
elements, so its stores are 16 bytes too.

- an MoE expert-combine kernel that added each row's sum once per lane of its row group

- the loss tail of a model whose tokens fit one wave's runs (Llama, 4096 tokens): 15.0

Recommended order:

1. **combo** -- 4.5 ms from one to four kernels a model: the fused AdamW step runs at
   about half Triton's time in every training model (1.5 ms a step saved on Llama). The
   smallest surface to upstream for a third of the gain.
2. **norm** -- 5.1 ms, now the largest, 3.4 of it BERT's f16 softmax/layernorm; the
   0.27-0.74x kernel wins above. It saves time on every model except ResNet NCHW (-0.04,
   within noise).
3. **pointwise** (with RNG) -- 1.5 ms, ahead on nine of the ten models (BERT -0.15). It
   is also the base the other stages share (indexing, casts, loads/stores, masks), so
   it lands with the first of them.
4. **row** -- +0.25 ms, all of it ResNet's BatchNorm-shaped reductions.
5. **column** -- +0.4 ms (GPT, ViT and Llama train each +0.1).
6. **tile**, **scan** -- at parity in models (+0.14 ms, and no scans in these models);
   upstream for coverage, not speed.

## Where it is complicated

These are the parts that took the most work, or that still limit it, roughly in order of
how much they matter.

### Choosing a layout per shape

Triton autotunes reduction configs; this backend picks one layout per kernel from rules,
each found by profiling a case that lost:

- column mode (64 lanes along x) when more loads are x-contiguous than r-contiguous,
  one vote per load;
- one wave per row whenever a wave can hold the row in registers (no LDS round trip),
  vectors narrowed when that tiles the row exactly (768 = 64 x 3 x 4), and one-wave
  blocks when a row fits in a wave;
- for short rows, every unrolled row's loads issued first, and the `xunroll` results of
  a lane group stored together, one per lane (`fdp.xstore`), instead of one partial
  store per row from lane 0;
- short rows read through a transpose (a load strided along the row but contiguous
  across rows, as a LayerNorm over an NCHW conv output's tokens) interleaved: 8 rows a
  wave, 8 lanes apart, so one element of 8 adjacent rows is one 16-byte run rather than
  8 cache lines. ViT's patch embedding + LayerNorm went 226 -> 101 µs (Triton 141). Only
  for rows up to 4096 elements: on ResNet's 200704-element BatchNorm rows it was 20x
  slower. A y-tiled reduction is accepted flat when its rows interleave this way;
- a row reduction with fewer rows than CUs takes a block as wide as its row allows (up
  to 1024 threads), for more loads in flight: BERT's loss tail, one row of 8192
  gathered logits, 36.3 -> 25.3 µs (Triton 26.4). This is checked before the one-wave
  rules, which had sent Llama's 4096-token loss tail to a single wave (15.0 µs). A
  gathered row also halves its elements a lane, down to 4, until it fills the block:
  12.1 µs at 1024 threads of 4 against 14.1 at 512 of 8 (Triton 12.1). A contiguous row
  keeps its 16-byte runs (a one-row 4096-wide sum went 1.8 -> 2.3 µs at 4);
- bf16/f16 column reductions whose loads are all contiguous along x give each lane two
  adjacent columns (`fdp.pair_load`, one 4-byte load for both): ViT's GELU-backward bias
  gradient 31.0 -> 19.4 µs in the model (Triton 22.7), `head_wgrad_bf16` 34.1 -> 25.3.
  Not f32, where the 8-byte loads were slower (85 -> 119 µs on `sum_cols_f32`);
- no more lanes on a column than it has rows: ResNet's BatchNorm stats finalize (64
  channels x 3 partial sums) had launched 1024 threads, 192 of them loading, combining
  through LDS across all of them; 7.7 -> 5.8 µs a kernel (Triton 6.0);
- scalar loads, one per thread, unrolled 8 deep when no load of the row vectorizes;
- pointwise vectors as wide as the widest stream allows (16 bytes), not the narrowest,
  and two elements a lane when the kernel has atomic adds per element; one-wave
  (64-thread) blocks by default (heads permute 25.3 -> 21.1 µs, 16M add 57 -> 50.5 µs).
  When every store is narrower than that (a narrowing cast), twice the elements, up to
  the stores' 16 bytes: `cast_bf16_24M` 44.4 -> 40.0 µs (Triton 42.9);
- one-wave blocks for rows that fit in a wave, except a bare reduction of short, fully
  unrolled rows, which keeps 256 threads: a sum of 32-wide rows 38.5 -> 35.7 µs;
- transposing tiles 16 wide by 64 when every store's pitch is at most 64 elements.

Where the best choice depends on context the rules cannot see -- what last touched the
inputs, mostly -- a kernel times a few candidates on its first call and keeps the fastest
(`fdp.pick_fastest`, on copies of the buffers it updates in place; skipped under CUDA
graph capture), as Triton autotunes: large pointwise kernels try two block shapes,
row reductions half and twice the lanes a row and half the elements a lane, column
reductions twice the threads (a column reduction too small to fill the GPU takes 1024
threads outright), transposing tiles a tile twice as wide (from 1M elements, against
4M for the rest). Candidates that never won
across the ten models' autotuned kernels were dropped. Each round of candidate calls is
queued behind a GPU sleep and timed as an average of back-to-back calls: Python launches
outlast a 20 µs kernel, and the fastest single call favoured high-variance candidates.
A round whose launches took longer to queue than the sleep covering them (a host busy
compiling other kernels) is thrown away and rerun with a longer sleep: next to a pytest
run, a heads permute had picked a variant 2.5x slower. Each call starts from the cache
state the kernel meets in the model, as far as the scheduler can tell: the 256 MB
last-level cache flushed, then the inputs the kernels just before it wrote or read
rewritten in place, so they sit in the cache dirty, as their producer left them. Timed
back to back, every input is cached instead: BERT's softmax-dropout backward, of whose
inputs only the matmul-written gradient is cached in the model, picked a variant at 115
µs against 100. Flushed with nothing rewritten, ResNet picked BatchNorm-backward
variants 0.1 ms a step slower, as their saved activations had just been read by the
convolution backward. The choice is kept on disk in the
Inductor cache, keyed by the candidates' source-hashed names and the GPU arch, so a warm
start neither re-times nor loads the losers (GPT-2 prefill warm start 5.2 -> 4.3 s,
Triton 4.2-4.6 s). In ResNet's training step an in-place conv bias add went
106 -> 84 µs this way (Triton 95), and a 64-wide softmax 71 -> 65 µs.

The access classifier that drives these sees through nested views
(`ModularIndexing`/`FloorDiv` of a contiguous index) and uses only the load/store
indices, recovered per node from `LoopBody.memory_usage`, because `finalize_indexing`
also sees `index_expr` values such as a split reduction's bounds check. Each rule has a
counterexample one step away, so they are written next to the measurements that justify
them.

### 2D tiles and transposes

A flat 1D layout cannot coalesce both the read and the write of a transpose: run flat, a
4096^2 transpose was 7.9x slower than Triton. Transposing kernels stage a 32x32 tile
through LDS, read with one thread mapping and written with the other; the tile pitch is
33 words so the column reads do not bank-conflict. 32x32 with 128 threads measured best:
a 64-wide f32 tile's 16.6 KiB of LDS leaves room for only three blocks a CU (54 µs vs 47
on an NCHW -> NHWC copy), and 256 threads were 55 µs vs 50 on a 4096^2 transpose. Wider
LDS accesses and XOR swizzles
were tried and did not help: these kernels are bound by global memory, not LDS. When
every store's pitch along the slow dimension is at most 64 elements (an NCHW -> NHWC
copy with 64 channels), the tile is 16 along the fast edge by 64 along the slow one, so
each store row is longer: 51.4 -> 48.2 µs on that copy (Triton 46.6). A staging pass
loads full vectors along the slow edge; when the block has more threads than one pass
of them covers (a 256-thread block over a 32 x 32 bf16 tile, 4 threads a row of 8), the
vector narrows, or the pass would run no iterations and leave the tile unloaded.

### Memory ordering the compiler cannot prove

Buffer loads and stores go through descriptors the backend cannot prove disjoint, so a
store blocks every later load from being hoisted above it. Pointwise kernels therefore
replay their loads for every run ahead of the body (into the trace-time vector cache;
unused loads are dead-code-eliminated), and short-row reductions issue every row's loads
before the first combine.

The persistent-row cache has the converse problem: a value cached before an in-place
store must not be reused after it. Stores record the buffer, and the cache is cleared for
it after the loop -- except the values the store itself wrote, which later passes read
from registers instead of reloading (masked stores enter them as the masked reload would
read them, 0 where masked off). Those stores are also held back to the end of their
loop: issued as the loop went, each run's store kept the next run's loads behind it,
and an embedding + LayerNorm loaded its three runs of a gathered row one memory round
trip after another (15.8 -> 15.2 µs on 4096 x 768 bf16; Triton 13.1).

### Narrow types and vector legalization

`<8 x i8>` / `<4 x i16>` buffer stores abort in LLVM's AMDGPU backend, so sub-dword vectors
are bitcast to i32/i16 words around every load and store. `torch.bool` is stored as a byte
but computed as i1, so storage and compute kinds are tracked separately. bf16/f16 values
are computed in f32 and rounded through their storage type exactly where Triton rounds,
so results match Triton bit for bit. Loads at a constant offset (a scalar parameter in a
buffer) are a single scalar load shared by every use, and a load the same across a
wave's lanes (a per-channel scale) is one scalar load from lane 0's offset
(`readfirstlane`): 86 -> 82 µs on ResNet's BatchNorm backward. Scalar loads read whole
dwords at aligned offsets, and a dword reaching past the descriptor reads as 0, so they
need a buffer extent that is a multiple of 4 bytes.

Constant offsets are kept apart from the lane-dependent part of an index (`fdp.Aff`) and
added last, so LLVM folds them into the buffer instruction's immediate: 53 address
instructions to 7 in a pointwise kernel's loop, though no measurable time.

### Atomics

A masked lane's offset is pushed out of bounds (0x7FFFFFFF), which hardware drops for
loads and stores -- but buffer atomics fault on it (`APERTURE_VIOLATION`), so masked
atomics are wrapped in an explicit `scf.if`. f32 uses the buffer atomic add. f16/bf16
have only packed two-element atomic adds: the element's half gets the value and its
neighbour -0.0, the additive identity, so the neighbour is left bit-for-bit unchanged.
gfx942 has the packed bf16 add only on global pointers (`buffer_atomic_pk_add_bf16` is
gfx950), so bf16 goes through an LLVM `atomicrmw` on the raw address. When a thread's two
elements are an aligned contiguous pair under one mask, they go out as one packed add:
a bf16 `index_put_(accumulate=True)` of 65536 x 1024 went 258 -> 184 µs (Triton 244).

A row reduction's result is held by every lane of the row's lane group, so a per-row
atomic (an MoE expert combine scattering each token's sum) is masked to the group's
first lane; unmasked, the sum was added 64 times. Which atomics are per row is decided
by the node's element count, not its reduction range: Inductor gives a pointwise node in
a reduction kernel an empty reduction range even when it runs per element, and taking
that for per row had uncapped an embedding gradient's scatter (28 -> 109 µs).

### Writing control flow from helpers

FlyDSL rewrites `if` and `for` into MLIR control flow only inside the kernel function's
AST. Helpers in `fdp` are not rewritten, so a dynamic branch there (the masked atomic) is
a hand-built `scf.IfOp`, and anything else that would branch on a runtime value is
expressed as selects.

### Static shapes and 32-bit indices only

AMD buffer descriptors carry an exact byte extent and take 32-bit byte offsets. The
extent comes from the buffer layout at codegen time, so dynamic shapes are refused, as
are kernels and buffers of 2^31 elements or more (indices are 32-bit).

A buffer of 2 GiB or more is past a descriptor's range. `fdp.rsrc` hands it back as a
raw 64-bit address (`fdp._Flat`), and loads, stores and atomics on it go through LLVM
global pointers: `base + zext(index) * itemsize`, with a select (loads) or a branch
(stores, atomics) for the mask that the descriptor would otherwise apply. Code
generation is the same; the choice happens at trace time from the extent. On Qwen3's
cross entropy over [8192, 151936] bf16 logits (2.5 GB, `bigce.py`), the three kernels
that used to fall back now run on FlyDSL: 8.4 ms a forward+backward step against
Triton's 14.4 (noisy GPUs).

### Compile time and caching

FlyDSL's disk cache keys on the kernel function's source and helpers in the same
directory, not on runtime modules like `fdp`; a runtime change would silently reuse stale
binaries. Each kernel's source is stamped with a fingerprint of the runtime modules.

Four things brought Qwen3-0.6B prefill's first step from 52.6 s to 26.0 s (Triton
25.3 s), measured one at a time:

| change | first step |
| --- | ---: |
| before | 52.6 s |
| launch the worker's code object through the static launcher, not `flyc.compile` (whose host-stub JIT is ~18 ms a kernel) | 43.7 s |
| decorate kernels only when compiling (`@flyc.kernel` rewrites the function's AST) | 42.1 s |
| cache keys name the kernel argument, not the graph buffer: the 28 layers' kernels had differed only in `'st3_buf32'` vs `'st3_buf62'`, so none were shared | 33.0 s |
| lower autotune candidates once per distinct source | 26.0 s |

This round took the ten-model suite's cold compile from 225 s to 164 s (Triton 158 s):

- autotune variants compile as separate worker jobs rather than one after another in a
  single worker, and precompile uses FlyDSL's compile-only mode, skipping kernels whose
  code object is already on disk;
- workers start importing and JIT-warming FlyDSL when the scheduler is constructed, take
  the gfx target from the parent (each worker's `rocm_agent_enumerator` took 0.2 s, over
  a second with 32 querying the driver at once), and import `buffer_ops` without the
  package that pulls in flex attention and the lowerings (0.45 s);
- worker compiles skip FlyDSL's per-op Python call-stack locations (10-18% of a
  kernel's compile);
- combo (foreach) sub-kernels whose bodies differ only in their buffers share one traced
  body, picking the member's descriptors under a uniform switch: GPT train cold first
  step 30.0 -> 24.3 s, and the AdamW kernel 567 -> 540 µs. Members of different sizes
  share it too when the body does not depend on the size, each owning its own number
  of blocks (Llama's AdamW kernel, the last compile of its optimizer graph, held the
  module load 1.37 -> 1.01 s);
- a warm start loads code objects that are already on disk in-process instead of
  through the pool (GPT train warm first step 7.0 -> 6.5 s, Triton 6.5), and reuses the
  cached autotune choice;
- once the pool is up, each kernel's code objects are submitted to it as the kernel is
  generated, instead of when Inductor's wrapper first asks for the kernel: BERT train
  cold first step 26.1 -> 25.0 s, Llama 23.7 -> 23.1 s (Triton 21.0).

What is left of the cold gap: about 3.9 s of pool startup in each model's first compile
(in the compile worker, outside this backend), the AdamW kernel's 1.2 s compile, and
the second autotune
candidate of large pointwise kernels (8 runs a thread), slow to compile but the pick on
16 of the 69 kernels it was offered.

On a cold ViT inference first step the pool is created at the first `torch.compile`
call, and its sidecar takes about 4 s (3.2 s importing torch, 0.9 s for Triton's cache
key and the device properties, 0.3 s for the FlyDSL preload) before it forks, which is
about when codegen ends. So every kernel compiles after codegen, and the module then
waits 0.94 s on 18 worker jobs against Triton's 0.24 s on 8. Most jobs take 0.15-0.6
s; the last is GELU's 8-runs-a-thread candidate, at 0.93 s, which wins 31 of the 95
large pointwise kernels it is offered across the ten models, by up to 55%. The AdamW
combo kernel (Llama train: 1.5 s, the end of the optimizer graph) is 0.28 s of FlyDSL's
AST rewrite, 0.34 s of tracing and 0.70 s of the MLIR/LLVM pipeline at `O2`. A call costs about 1-3 µs more host time than
Triton's launcher, invisible under CUDA graphs.

### Not supported

Sort, `bucketize`, `partial_accumulate`, bitcasts, scans inside `ops.masked` or chained
scans, dynamic shapes, cpp-wrapper and AOT Inductor. All of them fall back to Triton per
kernel, or raise under `flydsl.simd_strict`.

### Next

- Cold compile on small graphs: the pool's sidecar becomes ready only as codegen ends
  (about 4 s of startup, mostly importing torch), so a small graph's kernels all compile
  after it. Starting the pool earlier than the first `torch.compile`, or compiling the
  first kernels in-process while it starts, would hide that for both backends.
- Transposing tiles stay 2-6% behind Triton (`nchw_to_nhwc_f32`, `transpose_f32`): 4-byte
  stores from a tile row are narrower than Triton's. A 32 x 64 tile at 256 threads ran
  the NCHW -> NHWC copy at 40.8 µs in a kernel trace against 49.2 for the default, but
  52 against 48.6 under the suite's graph replay, and made no difference in ResNet; the
  two timings disagree on which tile is better.
- The per-op losers above and the standalone `sum_short_rows`. GPT's embedding +
  LayerNorm moves the same bytes as Triton's (same L2 hits, misses and DRAM requests)
  and runs fewer instructions, but its waves spend 60% more cycles waiting on memory
  (15.2 vs 13.1 µs alone). `softmax_bwd_512` is bimodal (39.8 or 45.3 µs): its two
  candidates are close with the last-level cache flushed, as `pick_fastest` times them,
  and apart in the suite's hot loop.
- The AdamW combo kernel is the longest single compile (1.0 s of Llama's, after its
  matrices of different sizes came to share a body). Its 2816 x 1024 and embedding
  members still take their own bodies for their unroll of 2; one unroll for the whole
  combo saved another 0.2 s but ran the kernel 1-2% slower.
- Per-kernel compile in the workers is what is left of the cold gap on training graphs
  (Llama 21.0-21.5 s against 19.5-19.9): the ROCm backend fixes the LLVM pipeline at
  `O2`, and FlyDSL's AST rewrite and tracing cost about as much again.

## Reproducing

```bash
export HIP_VISIBLE_DEVICES=0
# per-kernel table (CUDA-graph GPU time, GB/s, host call time); --only <cases>, --json out.json
python benchmarks/inductor_backends/flydsl_simd/bench_kernels.py
# whole models; --repeats N alternates backends and reports the median and spread,
# --gpus 0,1,.. runs models in parallel, one per GPU; --only <models>, --quick
python benchmarks/inductor_backends/flydsl_simd/bench_models.py --quick --repeats 3
# full-size HuggingFace Qwen3 (needs transformers and the configs in the HF cache)
python benchmarks/inductor_backends/flydsl_simd/bench_models.py --only qwen3_0p6b_train qwen3_0p6b_infer qwen3_8b_train qwen3_8b_infer --repeats 3
# stage ablation: one stage at a time
TORCHINDUCTOR_FLYDSL_SIMD_STAGES=combo python benchmarks/inductor_backends/flydsl_simd/bench_models.py --quick --repeats 3
# numerics of every model's loss and gradients against eager; --only <models>
python benchmarks/inductor_backends/flydsl_simd/check_models.py
# tests
python test/inductor/test_flydsl_simd.py
```

Timings move by up to 10% when another process uses any GPU of the machine, even a
different one; check `rocm-smi` shows the other GPUs idle for the length of a run.

Per-kernel profiles of a model: run a few warmed-up steps under
`rocprofv3 --kernel-trace --output-format csv`, take each kernel's median over the last
steps, and pair kernels by fused-op name (Triton's `triton_for_*` with FlyDSL's
`flydsl_fused__foreach*`). Count only the last calls of a Triton kernel: its autotuning
launches carry the same name. `torch.profiler` does not work on this ROCm build, and
CUDA-event timing around a single compiled call is not reliable for kernels under 100
µs (it put a 49 µs kernel at 70). Kernel durations and the suite's graph replay can also
rank two layouts differently: replay runs the kernel back to back, with its inputs and
outputs left in the last-level cache. For traffic, collect `FETCH_SIZE` and
`WRITE_SIZE` with `rocprofv3 --pmc` one counter a run: together they exceed one
hardware pass on gfx942, and the profiler aborts and leaves the process hung. For the
ISA, set
`FLYDSL_DUMP_IR=1 FLYDSL_DEBUG_DUMP_ASM=1 FLYDSL_DUMP_DIR=<dir>` and read
`21_final_isa.s`; Triton's is the `*.amdgcn` under `TORCHINDUCTOR_CACHE_DIR`.
