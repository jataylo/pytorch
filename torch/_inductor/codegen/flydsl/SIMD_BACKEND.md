# FlyDSL SIMD backend: pointwise, reduction, scan and foreach kernels

The FlexAttention path lowers a few FX subgraphs into a hand-written kernel. This backend
goes the other way: it replaces Triton as the code generator for Inductor's ordinary
fused kernels -- pointwise, reduction, scan, transposing and combo (foreach) kernels --
and emits a FlyDSL module per kernel instead of a Triton one. It is **ROCm only,
experimental and off by default**.

```bash
TORCHINDUCTOR_FLYDSL_SIMD=1 python train.py          # FlyDSL where it can, Triton elsewhere
TORCHINDUCTOR_FLYDSL_SIMD_STRICT=1 ...               # raise instead of falling back
TORCHINDUCTOR_FLYDSL_SIMD_STAGES=norm,combo ...      # FlyDSL for these kernel classes only
```

or `torch._inductor.config.flydsl.simd = True` / `flydsl.simd_strict = True`.

Every kernel it refuses goes to Triton unchanged, with the reason counted in
`counters["flydsl_simd"]` (`flydsl_simd_counters()` returns them). On the ten models of
the [model suite](#whole-models) nothing falls back: every pointwise, reduction and
foreach kernel Inductor builds for them is generated by FlyDSL.

## How a kernel is generated

The scheduler hands `FlyDSLSIMDScheduling.codegen_node_schedule` a fused node schedule.
It picks a tiling -- `{x}` for pointwise, `{x, r0_}` for a reduction or scan, `{y, x}`
when Inductor's tiling analysis finds a transpose -- and drives the normal `SIMDKernel`
codegen with `FlyDSLKernel`, whose ops overrides print every op as a call into `fdp`
(`fdp.add(tmp0, tmp1)`, `fdp.vload(...)`). Any `FlyDSLUnsupported` raised on the way rolls
the attempt back and the schedule is handed to Triton. A combo kernel is split into
groups of at most `combo_kernel_max_num_args` buffers, each generated as one FlyDSL
kernel whose blocks dispatch on the sub-kernel.

The emitted module holds the kernel and launcher as plain functions, decorated with
`@flyc.kernel` / `@flyc.jit` only when something compiles them, plus `_precompile` and
`_main`. In the compile worker `_precompile` compiles the kernel and writes its code
object (`<module>.<kernel>.hsaco`) beside the module; `_main` launches that through
`torch._C._StaticCudaLauncher`, so the main process never traces, JITs a host stub or
even decorates the kernel, and falls back to `flyc.compile` only when the file is missing
(for example when Inductor compiles in-process). FlyDSL traces the kernel in Python, so
the generated code is
ordinary Python that runs once at compile time: `range_constexpr` loops are unrolled
during tracing, and `fdp` keeps trace-time dictionaries (vector-load, vector-store and
persistent-row caches) that turn Inductor's per-element ops into vector instructions.

### Kernel classes

`FlyDSLKernel.stage` names the class a kernel falls in; `TORCHINDUCTOR_FLYDSL_SIMD_STAGES`
takes a comma-separated list of them and sends the rest to Triton, which is how the
[ablation](#which-stages-to-upstream-first) below was measured.

| stage | kernels | layout |
| --- | --- | --- |
| `pointwise` | elementwise, broadcasts, gathers/scatters, RNG, atomics | a thread owns `unroll` runs of `ept` contiguous elements, interleaved so each wave instruction covers one span |
| `tile` | transposes, NCHW <-> NHWC, head permutes | 32x32 LDS tile (pitch 33), 128-thread blocks, read and written with two thread mappings |
| `row` | pure reductions along a contiguous row (sum, amax, argmax, ...) | `tpr` lanes a row, `xunroll` rows a group, combined by DPP/butterfly shuffles, through LDS past a wave |
| `norm` | reductions whose result is used in the same kernel: softmax, layernorm, rmsnorm, cross-entropy and their backward | as `row`, with the row held in registers between passes when it fits |
| `column` | reductions along a strided dimension, split reductions (weight gradients, BatchNorm statistics) | 64 lanes along x, the waves of a block split r and combine through LDS |
| `scan` | `cumsum`/`cumprod`/associative scans along a row | a row's lanes scan their runs, then a cross-lane scan and a carry from the runs before |
| `combo` | foreach kernels (optimizer steps) | one block range per sub-kernel |

Rows of at most 16 vector runs a thread are *persistent*: unrolled entirely, held in
registers, and re-read from the trace-time cache by later passes (a layernorm's normalize
pass does not reload, and a row stored then re-read later in the kernel is forwarded
from the registers of the store). Longer rows run an `scf.for`.

**Chunked combines.** Inductor asks for one combine per element. Since a thread holds a
whole chunk at trace time, `fdp` combines it at once: sums as a balanced tree, online
softmax with one rescale per chunk, and -- for persistent rows -- softmax and variance in
two passes over registers (max then exp-sum; sum then squared deviations), as Triton does.

**Launch parameters** are written into the kernel as a comment, e.g.
`# row reduction xnumel=4096 rnumel=768 ept=4 unroll=1 tpr=64 stride=1 xunroll=1 persistent=True`,
and `TORCHINDUCTOR_FLYDSL_SIMD_TUNE="key=value,..."` overrides any of them for
experiments:

| key | applies to | meaning |
| --- | --- | --- |
| `ept`, `unroll` | pointwise | elements a run, runs a thread |
| `row_tpr`, `row_unroll`, `xunroll` | row, norm, scan | lanes a row, runs a lane, rows a lane group |
| `col_stride`, `col_unroll` | column | lanes along x, r steps a thread |
| `threads` | all | block size |
| `slp` | all | LLVM's SLP vectorizer on (`1`) or off (`0`); default on for pointwise and tile kernels, off for reductions, where it costs 5-15% |
| `merge_rows` | row | `0` stores short rows' results one row at a time from lane 0 |
| `force_flat` | tile | `1` runs a transpose with the flat layout |
| `autotune` | pointwise, tile, short rows | `0` keeps the heuristic's launch parameters instead of timing candidates on the first call |
| `wload` | pointwise | `0` turns off the wave-uniform scalar load of per-channel operands |
| `atomic_pair` | pointwise | `0` issues 16-bit atomic adds one element at a time |

## Where it is complicated

These are the parts that took the most work, or that still limit it, roughly in order of
how much they matter.

### Choosing a layout per shape

Triton autotunes reduction configs; this backend picks one layout per kernel from rules,
each found by profiling a case that lost:

- column mode (64 lanes along x) when more loads are x-contiguous than r-contiguous,
  one vote per load;
- one wave per row whenever a wave can hold the row in registers (no LDS round trip),
  vectors narrowed when that tiles the row exactly (768 = 64 x 3 x 4), and one-wave
  blocks when a row fits in a wave;
- for short rows, every unrolled row's loads issued first, and the `xunroll` results of
  a lane group stored together, one per lane (`fdp.xstore`), instead of one partial
  store per row from lane 0;
- scalar loads, one per thread, unrolled 8 deep when no load of the row vectorizes;
- pointwise vectors as wide as the widest stream allows (16 bytes), not the narrowest,
  and two elements a lane when the kernel has atomic adds.

Where the best choice depends on context the rules cannot see -- what last touched the
inputs, mostly -- a kernel times a few candidates on its first call and keeps the fastest
(`fdp.pick_fastest`, on copies of the buffers it updates in place; skipped under CUDA
graph capture), as Triton autotunes: large pointwise kernels try half-width vectors at
128 threads and 8 runs a thread, tile kernels 64 and 256 threads, short-row reductions
twice the rows a lane group and half the lanes a row, column reductions twice the
threads (a column reduction too small to fill the GPU takes 1024 threads outright). In ResNet's training step an
in-place conv bias add went 106 -> 84 µs this way (Triton 95), and a 64-wide softmax
71 -> 65 µs.

The access classifier that drives these sees through nested views
(`ModularIndexing`/`FloorDiv` of a contiguous index) and uses only the load/store
indices, recovered per node from `LoopBody.memory_usage`, because `finalize_indexing`
also sees `index_expr` values such as a split reduction's bounds check. Each rule has a
counterexample one step away, so they are written next to the measurements that justify
them.

### 2D tiles and transposes

A flat 1D layout cannot coalesce both the read and the write of a transpose: run flat, a
4096^2 transpose was 7.9x slower than Triton. Transposing kernels stage a 32x32 tile
through LDS, read with one thread mapping and written with the other; the tile pitch is
33 words so the column reads do not bank-conflict. 32x32 with 128 threads measured best:
a 64-wide f32 tile's 16.6 KiB of LDS leaves room for only three blocks a CU (54 µs vs 47
on an NCHW -> NHWC copy), and 256 threads were 55 µs vs 50 on a 4096^2 transpose. Wider
LDS accesses and XOR swizzles
were tried and did not help: these kernels are bound by global memory, not LDS.

### Memory ordering the compiler cannot prove

Buffer loads and stores go through descriptors the backend cannot prove disjoint, so a
store blocks every later load from being hoisted above it. Pointwise kernels therefore
replay their loads for every run ahead of the body (into the trace-time vector cache;
unused loads are dead-code-eliminated), and short-row reductions issue every row's loads
before the first combine.

The persistent-row cache has the converse problem: a value cached before an in-place
store must not be reused after it. Stores record the buffer, and the cache is cleared for
it after the loop -- except the values the store itself wrote, which later passes read
from registers instead of reloading.

### Narrow types and vector legalization

`<8 x i8>` / `<4 x i16>` buffer stores abort in LLVM's AMDGPU backend, so sub-dword vectors
are bitcast to i32/i16 words around every load and store. `torch.bool` is stored as a byte
but computed as i1, so storage and compute kinds are tracked separately. bf16/f16 values
are computed in f32 and rounded through their storage type exactly where Triton rounds,
so results match Triton bit for bit. Loads at a constant offset (a scalar parameter in a
buffer) are a single scalar load shared by every use, and a load the same across a
wave's lanes (a per-channel scale) is one scalar load from lane 0's offset
(`readfirstlane`): 86 -> 82 µs on ResNet's BatchNorm backward. Scalar loads read whole
dwords at aligned offsets, and a dword reaching past the descriptor reads as 0, so they
need a buffer extent that is a multiple of 4 bytes.

Constant offsets are kept apart from the lane-dependent part of an index (`fdp.Aff`) and
added last, so LLVM folds them into the buffer instruction's immediate: 53 address
instructions to 7 in a pointwise kernel's loop, though no measurable time.

### Atomics

A masked lane's offset is pushed out of bounds (0x7FFFFFFF), which hardware drops for
loads and stores -- but buffer atomics fault on it (`APERTURE_VIOLATION`), so masked
atomics are wrapped in an explicit `scf.if`. f32 uses the buffer atomic add. f16/bf16
have only packed two-element atomic adds: the element's half gets the value and its
neighbour -0.0, the additive identity, so the neighbour is left bit-for-bit unchanged.
gfx942 has the packed bf16 add only on global pointers (`buffer_atomic_pk_add_bf16` is
gfx950), so bf16 goes through an LLVM `atomicrmw` on the raw address. When a thread's two
elements are an aligned contiguous pair under one mask, they go out as one packed add:
a bf16 `index_put_(accumulate=True)` of 65536 x 1024 went 258 -> 184 µs (Triton 244).

### Writing control flow from helpers

FlyDSL rewrites `if` and `for` into MLIR control flow only inside the kernel function's
AST. Helpers in `fdp` are not rewritten, so a dynamic branch there (the masked atomic) is
a hand-built `scf.IfOp`, and anything else that would branch on a runtime value is
expressed as selects.

### Static shapes and 32-bit offsets only

AMD buffer descriptors carry an exact byte extent and take 32-bit offsets. The extent
comes from the buffer layout at codegen time, so dynamic shapes are refused, as are
buffers of 2 GiB or more and kernels of 2^31 elements or more. Lifting either needs the
extent passed at launch and 64-bit address arithmetic outside the descriptor.

### Compile time and caching

FlyDSL's disk cache keys on the kernel function's source and helpers in the same
directory, not on runtime modules like `fdp`; a runtime change would silently reuse stale
binaries. Each kernel's source is stamped with a fingerprint of the runtime modules.

Four things brought Qwen3-0.6B prefill's first step from 52.6 s to 26.0 s (Triton
25.3 s), measured one at a time:

| change | first step |
| --- | ---: |
| before | 52.6 s |
| launch the worker's code object through the static launcher, not `flyc.compile` (whose host-stub JIT is ~18 ms a kernel) | 43.7 s |
| decorate kernels only when compiling (`@flyc.kernel` rewrites the function's AST) | 42.1 s |
| cache keys name the kernel argument, not the graph buffer: the 28 layers' kernels had differed only in `'st3_buf32'` vs `'st3_buf62'`, so none were shared | 33.0 s |
| lower autotune candidates once per distinct source | 26.0 s |

What remains over Triton is the candidates' lowering for each distinct kernel and their
first-call timing (0.4 s on the prefill). A call costs about 1-3 µs more host time than
Triton's launcher, invisible under CUDA graphs.

### Not supported

Sort, `bucketize`, `partial_accumulate`, bitcasts, scans inside `ops.masked` or chained
scans, dynamic shapes, cpp-wrapper and AOT Inductor. All of them fall back to Triton per
kernel, or raise under `flydsl.simd_strict`.

### Next

- Cold compile: an autotuned kernel compiles its three variants in one worker, one after
  another; submitting them as separate jobs (in `async_compile`) would overlap them.
  FlyDSL's per-kernel compile (~1 s, 4.5 s for a foreach AdamW kernel) is the rest.
- `sin`/`cos` with branch-free argument reduction, for RoPE computed in the kernel.
- Buffers of 2 GiB or more (large-vocabulary logits) fall back to Triton.
- An NCHW -> NHWC copy stays 10% behind Triton at every tile size and block size tried.
